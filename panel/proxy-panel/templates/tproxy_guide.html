Architecture

Telegram WEB Proxy consists of 3 components:

Telegram Client
    |  MTProto framing + encryption
    v
WebView (local adapter)
    |  multiplexed streams
    v
carrier (HTTPS / WebSocket)  <-- carrier_mode defines transport
    |
    v
tproxy-server (:8090)  <-- Go relay
    |  TCP
    v
mtproto-proxy (:2398)  <-- official MTProxy from Telegram
    |  MTProto
    v
Telegram DC (91.108.x.x:8888)

Carrier Modes

Carrier mode defines how the client WebView sends MTProto data through HTTP to tproxy-server.

https (default)

All logical sessions are multiplexed in one HTTPS connection.

  • Simplest mode, maximum compatibility
  • One connection becomes bottleneck under high load
  • Recommended for: small deployments, testing

https-lanes

Each logical session gets its own HTTPS request (independent "lanes").

  • Better isolation between sessions
  • Easier load balancing
  • Recommended for: medium-load servers

websocket

One multiplexed WebSocket connection for all sessions.

  • No HTTP request overhead (connection established once)
  • Full-duplex channel = lower latency
  • May not work behind some proxies/CDNs (upgrade header blocked)
  • Recommended for: persistent connections without intermediate proxies

websocket-lanes

Each session = separate WebSocket.

  • Maximum isolation + low WebSocket overhead
  • More resources (separate WS per session)
  • Recommended for: high-load servers, user isolation

How to choose

  1. Start with https - default, works everywhere
  2. Need user isolation? → https-lanes or websocket-lanes
  3. No intermediate proxies/CDN + need low latency? → websocket or websocket-lanes
  4. High load → websocket-lanes
