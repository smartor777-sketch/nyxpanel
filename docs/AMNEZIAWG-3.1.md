# AmneziaWG 3.1 — параметры обфускации

Справочник по параметрам AmneziaWG 3.1, которые панель копирует в
клиентские конфиги. Дополняет `SERVER_CONFIG.md` (раздел AmneziaWG) и
`REQUIREMENTS.md` (версии модуля и tools).

Проверено на стенде `dev`: модуль `3.1.20260906`, tools `3.1.20260812`,
интерфейс `awg0`.

---

## 1. Полный набор параметров

| Параметр | Что делает | Должен совпадать с клиентом |
|---|---|---|
| `Jc`, `Jmin`, `Jmax` | количество и размер «мусорных» пакетов перед handshake | для единообразия |
| `S1`–`S4` | padding init / response / cookie / transport пакетов | **да** |
| `H1`–`H4` | диапазоны значений типа заголовка (init / response / cookie / transport) | **да** |
| `I1`–`I5` | до пяти шаблонов фейковых пакетов перед handshake | нет (получатель игнорирует) |
| `HeaderProtectionKey` | шифрует заголовки сообщений | **да** |
| `RandomTrailers` | случайный «хвост» в конце пакетов | **да** |
| `DisableCookies` | отключает cookie-ответы WireGuard | **да** |
| `ContentPaddingAddition` | дополнительный padding контентных пакетов | для единообразия |
| `RekeyAfterTime` | интервал rekey (диапазон) | для единообразия |
| `RekeyTimeout` | таймаут rekey (диапазон) | для единообразия |
| `RejectAfterTime` | через сколько отбрасывать сессию (диапазон) | для единообразия |
| `KeepaliveTimeout` | интервал keepalive (диапазон) | для единообразия |
| `MaxHandshakeAttempts` | число попыток handshake (диапазон) | для единообразия |

> «Должен совпадать» означает: если значения разойдутся, handshake или
> разбор пакетов сломаются. Остальные параметры панель копирует, чтобы
> профиль был консистентным, но их совпадение не критично.

---

## 2. I1–I5: фейковые пакеты перед handshake

`I1`–`I5` — это **пять необязательных слотов** для пакетов-приманок.
Это не «уровни» и не версии: номера задают только порядок отправки.

### Когда отправляются

При инициации handshake (клиент, а также сервер при rekey) модуль:

1. отправляет все настроенные `I1` → `I5` по порядку;
2. затем `Jc` обычных мусорных пакетов размера `Jmin..Jmax`;
3. и только потом — настоящий handshake initiation.

Получатель пакеты `I1`–`I5` не разбирает: для туннеля это шум. Они нужны,
чтобы DPI видел перед handshake правдоподобную последовательность
пакетов другого протокола, а не «голый WireGuard».

### Мини-язык шаблонов

| Тег | Что вставляет | Пример |
|---|---|---|
| `<b 0x...>` | литеральные байты из hex | `<b 0x16030100>` |
| `<r N>` | N случайных байт | `<r 64>` |
| `<rc N>` | N случайных латинских букв | `<rc 16>` |
| `<rd N>` | N случайных цифр | `<rd 8>` |
| `<c>` | 4-байтовый счётчик (стартует случайно, растёт на каждый I-пакет) | `<c>` |
| `<t>` | 4-байтовый Unix timestamp | `<t>` |

Теги можно комбинировать в одной строке:

```ini
# имитация начала TLS ClientHello + случайный хвост
I1 = <b 0x16030100><r 32>

# «сессионный идентификатор» из цифр
I2 = <rd 8>
```

### Что сейчас на `dev`

```ini
I1 = <r 64>   # 64 случайных байта
I2 = <rd 8>   # 8 случайных цифр
# I3, I4, I5 не заданы
```

Это «случайный прелюд», а не имитация конкретного протокола. Для базовой
задачи — сбить сигнатуру — работает. Для правдоподобной маскировки под
TLS/QUIC шаблоны собираются вручную.

### Нужно ли совпадение I1–I5

Строго — нет: получатель эти пакеты игнорирует, это исходящая маскировка.
Но панель копирует `I1`–`I5` в клиентский конфиг, чтобы клиент отправлял
такой же прелюд. Если значения на сервере и клиенте разные, туннель
работает, но рисунок трафика будет разным.

### Где это в коде

| Файл (DKMS-исходники) | Что |
|---|---|
| `junk.c` | парсер мини-языка и модификаторы (`b`, `c`, `t`, `r`, `rc`, `rd`) |
| `send.c` | отправка `I1`–`I5` перед handshake |
| `netlink.c` | применение `WGDEVICE_A_I1..I5` |
| `device.h` | `struct jp_spec ispecs[5]` |

Исходники на стенде: `/usr/src/amneziawg-3.1.20260906/`.

## 3. Пример полного 3.1-блока

```ini
[Interface]
PrivateKey = <hidden>
Address = 10.20.20.2/32
MTU = 1280

HeaderProtectionKey = <32 байта base64>
Jc = 5
Jmin = 50
Jmax = 200
S1 = 64
S2 = 78
S3 = 48
S4 = 32
H1 = 1000000-1100000
H2 = 2000000-2100000
H3 = 3000000-3100000
H4 = 4000000-4100000
I1 = <r 64>
I2 = <rd 8>
ContentPaddingAddition = 8-32
RekeyAfterTime = 100-140
RekeyTimeout = 5-10
RejectAfterTime = 180-200
KeepaliveTimeout = 10-15
MaxHandshakeAttempts = 18-20
RandomTrailers = on
DisableCookies = on
```

Ограничения:

- `HeaderProtectionKey` требует `S1–S4 ≥ 12` (размер nonce
  `HEADER_PROTECTION_NONCE_SIZE = 12`); при меньшем значении ядро вернёт
  `EINVAL`.
- `H1`–`H4` не должны пересекаться между собой.
- Старые клиенты (AmneziaWG 2.x и ниже) 3.1-профиль не поймут — нужен
  AmneziaVPN ≥ 5.0.1.5.

## 4. Проверка на сервере

```bash
# версии
modinfo -F version amneziawg
awg --version

# параметры применены ядром, а не только лежат в файле
awg show awg0

# полный конфиг интерфейса (секреты скрыть)
awg showconf awg0 | sed -E 's/(PrivateKey|PresharedKey|HeaderProtectionKey) = .*/\1 = <hidden>/'
```

`awg show awg0` должен показать `header protection key`, `random trailers:
on`, `disable cookies: on` и диапазоны таймингов — это значит, что 3.1
включён на уровне интерфейса.

## 5. Связь с панелью

`bin/proxy_manager.sh`, функция `add_awg_user`, копирует параметры из
серверного конфига в клиентский. Список зафиксирован тестом
`tests/test_awg_31_params.sh`: если параметр выпадет из grep-шаблона,
тест упадёт.

При добавлении нового 3.1-параметра обновить:

1. grep-шаблон в `bin/proxy_manager.sh`;
2. список в `tests/test_awg_31_params.sh`;
3. этот документ и `SERVER_CONFIG.md`.
